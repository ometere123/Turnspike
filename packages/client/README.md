# @turnspike-qie/client

Agent-side client for Turnspike APIs. It turns a Turnspike HTTP 402 into a payment on QIE, but only inside a spending policy you define, and it survives restarts without paying twice. Install: `npm install @turnspike-qie/client ethers`.

```ts
import { TurnspikeClient, FileJournal, QIE_MAINNET, parseUnits } from "@turnspike-qie/client";

const client = new TurnspikeClient({
  signer,                                   // the AGENT signer: keystore wallet, KMS or remote signer. Never the owner key.
  owner: "0xOwner...",                      // whose allowance account pays
  network: QIE_MAINNET,                     // trusted chain, settlement contract and QUSDC
  policy: {
    payees: [{ origin: "https://api.example.com", merchant: "0xMerchant..." }], // nobody else is ever paid
    maxPriceBase: parseUnits("0.005"),      // hard ceiling per request
  },
  approve: (quote) => quote.gasCostWei < 10n ** 15n, // your own rule, called before every payment
  journal: new FileJournal(".turnspike/journal.json"),
});

const r = await client.fetch("https://api.example.com/v1/report/7", {}, { idempotencyKey: "report-7" });
if (r.ok && r.kind === "paid") console.log(await r.response.json(), r.payment.explorerUrl);
else if (!r.ok && r.paid) await client.resume("report-7"); // paid, not yet delivered: collect later
```

## What happens on `fetch`
1. The request is sent. A non-402 answer is returned as `{ kind: "free" }`.
2. The 402 body is validated (`protocol` must be `turnspike/1` when present).
3. Trust checks, all local: the request origin **and** the merchant named in the challenge must be a listed payee; chain id, contract and token must match the trusted network; the price must be within every ceiling; the challenge must not be about to expire.
4. Chain checks: the signer is the owner's authorized agent, the account is not paused, the merchant is on the owner's on-chain allowlist, the request id is unused, the price fits the per-call cap, today's remaining cap and the balance, and the agent has enough QIE for gas (estimate x gas price, plus `minGasReserveWei`, under `maxGasCostWei`).
5. `approve(quote)` is called. With `dryRun: true` the quote is returned and nothing is sent.
6. The nonce and head block are journaled, then `pay(owner, merchant, requestId, amount)` is broadcast and the hash journaled.
7. After `confirmations` the proof `X-Payment: base64({requestId, txHash, sig})` is presented, retrying 202, 429 and 5xx answers with backoff until `redeemTimeoutMs`.

Every refusal in steps 2 to 5 costs nothing. **A payment that reached the chain cannot be reversed because a later HTTP step failed.** The result then has `paid: true`; keep the key and call `resume(key)`.

## Restart safety
The journal records each purchase by `idempotencyKey`. `fetch` with a known key, or `resume(key)`, continues from the recorded state: it redeems a confirmed payment, waits for a broadcast one, and for a crash between broadcast and saving the hash it checks `isUsed` on the contract and finds the transaction from the `Paid` log. The contract also refuses a second payment of the same request id. Since 0.1.1: expiry is checked again immediately before sending, so a slow `approve` cannot pay an expired challenge; a submission that fails ambiguously (timeout, dropped connection) keeps the record open instead of marking it failed, so the key is not released for a new purchase; a recorded challenge that was never sent is checked again against today's payee list, price ceiling, owner policy, gas and `approve` before it is paid; and a key is bound to its method, URL and body (a string, `URLSearchParams` or byte body is required when a key is used). Records written by 0.1.0 carry no body fingerprint, so they are reused only for a body-less GET or HEAD of the same URL; anything else is an `idempotency_conflict` (`resume(key)` still collects them).

### Idempotency guarantees
These guarantees cover one purchase attempt at a time. A key is released for a new attempt (with a new requestId) only after its record is `failed`, and the client writes `failed` only when the attempt cannot charge: nothing was sent (still reserved, never sent, expired or definitively rejected before sending), or its own transaction reverted, or its recorded nonce was consumed, and in each of the last two cases the contract still shows its requestId unused. If a record is marked `failed` by anything else (a custom journal, manual editing, an operator) while a transaction is in flight, or a chain reorganisation undoes the evidence, the key can be reused and **both attempts can charge**: "one key, one payment" is not guaranteed across failed-key reuse.

- **One attempt, one requestId.** Before asking for a challenge, `fetch` claims the key with an atomic compare-and-set on the journal (`Journal.swap`, conditional on the record's revision `rev`, which every write increments). Only the claiming call can record a challenge under the key, and every later path (resume, retries, recovery) of that attempt pays only that challenge's requestId, which the contract will accept at most once. A concurrent call with the same key gets `payment_pending` with `maybePaid: true` and pays nothing; call `resume(key)` later.
- **No stale writer wins.** Every decision (reserve, record a challenge, start paying, mark failed, release, take over) is written only against the exact revision the worker read; a worker with an outdated copy loses and reports the newer record instead. Facts (broadcast, confirmed, delivered) only move a record forward and override `failed`. So a completed purchase can never be reopened by a competing worker's failure, and of two workers holding the same copy only one can start a payment.
- **Attempts never mix.** Each purchase attempt under a key carries an immutable `attempt` id (0.1.0 records: the challenge requestId). When a failed key is reused, a late broadcast, confirmation or delivery from the earlier attempt is never written into, or read from, the newer record; that earlier attempt finishes with its own in-memory copy and returns its own resource and proof to its own caller. A stale worker that finds a different attempt under the key reports `payment_pending` with `maybePaid: true` and its own requestId, never the other attempt's response. Limitation: after such a reuse the earlier attempt is no longer in the journal and has lost journal-based recovery. If its process stops before it finishes, `resume(key)` reaches the newer attempt, and the earlier payment can be found only on chain (a `Paid` event for its requestId from the agent). Its transaction hash may never have reached its caller: the process may have stopped before returning, or the submission may have ended as `payment_pending` before a hash was known. Callers that need to account for every charge should reconcile `Paid` events for the agent, not the journal alone.
- **Single process:** guaranteed with `MemoryJournal`, `FileJournal`, or a custom journal without `swap` as long as all clients share the same journal object (the client then serializes claims in-process).
- **Several processes on one machine:** guaranteed with a shared `FileJournal` path on a local disk. Every read-modify-write holds an O_EXCL lock file naming its owner (host, pid, token). A lock is never taken from a live process, however long it pauses; it is removed only when its owner pid on this host has exited, under a second O_EXCL lock. A lock from another host, an unreadable lock, or one whose pid was reused is never removed: operations wait `lockWaitMs` (default 60 s) and then fail, and an operator must clear it. Not for network or shared file systems.
- **Several machines:** supply a custom `Journal` whose `swap` is an atomic conditional write in a shared store (a database transaction or conditional put). A journal without `swap` gives no cross-process guarantee.
- **Crash before a challenge was recorded:** the key stays `reserved`; after `reservationTimeoutSeconds` (default 300) another call takes it over, and the takeover is conditional on that exact reserved revision: if the original call records its challenge first, the takeover fails, and if the takeover wins, the original call can no longer record a challenge. Nothing can have been paid in that state.
- **What is not guaranteed:** distinct keys for the same resource are distinct purchases; and if a hidden earlier submission and a re-sent payment of the same challenge both reach the chain, only one can charge (same nonce, same requestId) but the other may still cost gas. Journals hold the challenge `sig` (the secret half of the proof): protect the file, or supply your own `Journal` backed by your secret store. Share an agent key across processes only through one shared journal (see above).

## Paying a challenge for another protocol layer (0.2.0, unreleased)
`payChallenge(challenge, { url, method, bodyHash?, purchaseKey, maxPriceBase? })` pays a challenge the caller already received (the `@turnspike-qie/x402` package uses it) and returns `{ ok: true, proof: { requestId, txHash, sig }, payment, resumed }` once the payment has `confirmations`. It performs no HTTP: the caller presents the proof. It runs every check `fetch` runs, with the payee allowlist applied to the origin of `url` (pass the URL actually fetched) and the challenge's merchant.
- **One key, one purchase.** The purchase is recorded under `purchaseKey` with the same revision-fenced journal. Calling again with the same key and the same challenge resumes it: the same proof once confirmed, `maybePaid` while unresolved, never a second payment. A different challenge (or a different method, URL or `bodyHash`) under a key that is not `failed` is refused with `idempotency_conflict` and pays nothing; when the existing purchase is confirmed, that result carries `paid: true` and its `proof`, so the caller can present it again instead of paying again. `bodyHash` should be the keccak256 hex of the body bytes if the same key may also be used with `fetch`.
- **After presenting.** `markProofPresented(key, requestId?)` and `markDelivered(key, requestId?)` record the `proof_presented` and `delivered` facts. They only move a record forward and return false, writing nothing, unless the key holds a confirmed payment (of that requestId, when given).
- **Startup recovery.** `pendingPurchases()` lists this owner's and agent's unfinished records. `recoverPending()` settles each one from the chain, one at a time, with the existing resume rules: it confirms broadcast payments, finds payments whose hash was never saved (`isUsed`, the recorded nonce, the `Paid` log), re-sends only at the recorded nonce, closes reservations abandoned for `reservationTimeoutSeconds` and expired never-sent challenges, and returns each proof. Fresh challenges that were never sent are left alone unless `{ payUnsent: true }`. It performs no HTTP: present the proofs, or call `resume(key, init)` for purchases made with `fetch`. A record whose nonce was consumed by another transaction while its requestId stayed unused was provably never charged; the resume rules pay it (once) if its challenge is still fresh.

### Several processes sharing one agent key
A journal may implement `allocateNonce(agent, chainPendingNonce, { nonce? })`; `MemoryJournal` and `FileJournal` do (FileJournal in a sibling file `<path>.nonces`, under the same O_EXCL lock). The client then takes each new payment's nonce from the journal instead of the chain's pending count, which concurrent processes would all read alike. The rule: forget reservations the chain has passed; reclaim reservations whose holder process on this host has exited, and any older than `nonceLeaseTtlMs` (default 10 minutes); reuse the lowest free gap at or above the chain's pending nonce; otherwise hand out `max(chainPending, next)`. A lease is released as `sent` as soon as the transaction may be in a mempool (blocked until the chain passes it), or as not sent when the node refused it (handed out again, so later transactions do not wait behind a gap). A resend claims its recorded nonce explicitly. Tested with two OS processes making 10 concurrent purchases each with one key: 20 payments, 20 distinct nonces, no errors. Limits: a transaction sent with the agent key outside the journal can still collide with a reserved nonce (the result is an ambiguous `payment_pending`, never a second charge); a reservation reclaimed by TTL from a process that is only paused, or a dead process's transaction waiting behind a gap, can collide the same way. Use a signer that honours the nonce it is given (ethers `NonceManager` overrides it). Not for several machines: supply a journal whose `allocateNonce` is atomic in a shared store.

## Results
`{ ok: true, kind: "free" | "paid" | "dry_run" }` or `{ ok: false, error, message, paid, payment?, quote? }` where `error` is one of `invalid_challenge`, `unsupported_protocol`, `untrusted_destination`, `wrong_network`, `price_above_max`, `challenge_expired`, `not_authorized_agent`, `paused`, `merchant_not_allowed`, `over_per_call_cap`, `over_daily_cap`, `insufficient_balance`, `insufficient_gas`, `gas_cost_above_max`, `declined`, `already_paid`, `tx_reverted`, `tx_timeout`, `rpc_unavailable`, `gateway_unavailable`, `redeem_rejected`, `redeem_timeout`, `request_failed`, `payment_pending`, `idempotency_conflict`.

Failures carry `paid` and `maybePaid`. `paid: true`: QUSDC moved. `maybePaid: true` (with `paid: false`): the outcome is not known yet, for example a submission timed out, a transaction at the recorded nonce is pending or unresolved (even if the challenge has since expired), or another call holds the key. The key stays reserved; call `resume(key)` later and never start a new purchase for that request. Only a result with neither flag means nothing was or can be charged. `idempotency_conflict` means the key already belongs to a different method, URL or body; nothing was paid.

## Cost on QIE (measured)
One payment used 92,159 gas, 0.000104 QIE at 1.125 gwei, on 2026-11-19 (`evidence/M8_sdk_mainnet.md`). Gas price varies; the client always uses a live estimate.
